# Task — Gate 2026-09-17

## Obiettivo

Chiudere il modulo canonico **Task** senza creare nuovi moduli o writer, mantenendo il Task manager esistente come proprietario di stato, priorità, scadenza, modifica manuale e undo.

## Contratto implementato

### Task manuali e automatici

- I task manuali mantengono `origin: manual` e non vengono riconciliati automaticamente se non possiedono un collegamento esplicito a una causa.
- I task generati da Audit usano `origin: audit`, `automatic: true` e un `taskLinks.problemKey` stabile.
- I task creati da Opportunità usano `origin: opportunity`, `automatic: true`, `taskLinks.opportunityId/opportunityKey` e, quando disponibile, anche `problemKey`.
- I task legacy Audit ricevono il linkage al successivo passaggio di `reconcileAuditTasks`, senza perdere ID, note o scadenza.

### Collegamento alla causa

`taskLinks` è il contratto persistito:

- `problemKey` → problema Audit/unified problem;
- `correctionId` → record Correzioni;
- `opportunityId` / `opportunityKey` → opportunità SEO.

Quando esiste una correzione per il `problemKey`, il reconciler globale aggiunge il `correctionId` più recente senza eliminare gli altri riferimenti.

### Stato, priorità e scadenza

Il Task manager esistente resta source of truth per:

- `status`: Da fare / In corso / In revisione / Completato;
- `priority`: Alta / Media / Bassa;
- `due`: scadenza o Da pianificare;
- note e dettagli utente.

La riconciliazione di causa modifica solo i campi necessari alla chiusura/riapertura e conserva priorità, scadenza e note.

### Undo

La riconciliazione produce normali delta Task. `taskChange()` + `undoTaskChange()` continuano a usare il controllo exact-after/stale-check: l'undo è consentito solo se il task non è cambiato dopo l'operazione da annullare.

### Deduplica

`sameTask()` usa prima l'identità canonica della causa. Due task con lo stesso `problemKey`, `correctionId` o `opportunityId` vengono riconosciuti come la stessa attività anche se il titolo cambia. Rimangono i fallback storici per query e identità Audit.

## Gate di riconciliazione

Una Task collegata viene chiusa automaticamente solo quando esiste evidenza di causa chiusa:

1. problema `resolved` o `intentional`;
2. correzione `Verificato`, con `writeConfirmed !== false` e senza `completionGatePending`;
3. opportunità esplicitamente marcata `resolved/Risolta/Completata`.

Una Task completata non dimostra mai da sola la risoluzione SEO: `task_completed` non porta `problemState` a `resolved` nel reliability model.

Se la causa torna attiva/reappeared, viene riaperta **solo** una Task precedentemente chiusa dal reconciler (`causeReconciled: true`). Una Task chiusa manualmente dall'utente non viene riaperta dal nuovo reconciler.

## UI

La pagina Task mantiene il manager esistente e aggiunge un pannello di provenienza con:

- conteggio Task manuali;
- Task automatici;
- Task con linkage;
- Task chiuse per riconciliazione;
- causa visibile per Task;
- CTA diretta verso Problema, Correzione o Opportunità.

## Release Gate

Il Gate richiede:

- test chiusura problema → Task completata;
- test correzione verificata → Task completata;
- correzione non verificata → nessuna chiusura;
- regressione → riapertura soltanto della Task auto-riconciliata;
- Task manuale senza linkage invariata;
- deduplica per causa canonica;
- persistenza linkage;
- backfill Audit senza perdita note/scadenza/correctionId;
- undo esatto della riconciliazione;
- lint, unit/integration/storage, build e browser QA completi.
